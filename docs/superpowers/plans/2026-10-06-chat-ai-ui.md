# 第七章：UI 响应协议与 Structured Output（feat/ai-ui）

> 从 `feat/db-vector` 切出 `feat/ai-ui`。目标：让模型输出「可渲染的 UI 组件」而非纯文本——用 Zod discriminatedUnion 定义协议，用 `withStructuredOutput` 约束模型，用确定性状态机承接用户在 UI 上的操作。

## 实现 Prompt 原文

在 services/chat 的 LangChain 层中，设计 UI 响应协议并实现 Structured Output 约束，严格按以下要求执行：

1. 类型定义：新建 `services/chat/src/llm/ui-protocol/ui-types.ts`，定义 UIResponse 联合类型（text / selection / form / confirmation / card / steps / table / action_buttons 八种组件，`type` 字段区分），定义 UIAction 表示用户操作回传
2. Zod Schema：新建 `ui-schemas.ts`，为每个组件类型定义 Zod Schema，`z.discriminatedUnion` 基于 type 精确匹配，导出 `uiResponseSchema` 和 `aiUIResponseSchema`
3. UI 响应服务（Structured Output）：新建 `ui-response.service.ts`，`model.withStructuredOutput(aiUIResponseSchema)` 约束模型输出；`generateUIResponse(input, history?, context?)`：System Prompt 明确说明何时使用哪种组件；返回 AIUIResponse
4. 组件类型和字段贴近业务场景：需求分析系统流程
5. UI Action 处理：`ui-flow.service.ts` 实现 `handleAction(sessionId, action)`，根据用户在 UI 上的操作推进确定性状态机
6. 新增路由 `@Controller('api/ui-chat')`：POST chat（`{sessionId, input}` 返回 AIUIResponse）、POST action（`{sessionId, action}` 处理 UI 操作并返回下一步）

测试：输入「我要提一个新需求」→ selection；输入「查看需求 REQ-20240315-001」→ card；提交需求分析 → confirmation + steps。

## 关键设计

### 协议分层：模型只负责「选组件 + 填内容」，不负责「定协议」

```
POST /api/ui-chat/chat（自由输入，LLM 路径）
  UiChatController → UiFlowService.recordUserInput（会话历史/阶段）
                   → UiResponseService.generateUIResponse
                       chatModel().withStructuredOutput(aiUIResponseSchema, { method: 'functionCalling' })
                   → UiFlowService.recordAssistantResponse
POST /api/ui-chat/action（UI 操作回传，确定性路径，不经过模型）
  UiChatController → UiFlowService.handleAction（状态机：intake → collect_details → confirm → analyzing → completed）
```

- **两条路径刻意分开**：自由输入走 LLM（Structured Output 保证输出恒为合法协议对象）；表单提交、确认、行选择这类 UI 操作是确定性转移，走纯代码状态机，不花 token、不可被模型幻觉带偏。
- **类型与 schema 双向校验**：`ui-types.ts` 手写 TS 接口，`ui-schemas.ts` 定义 Zod schema，文件底部用四个编译期赋值断言 `z.infer` 与手写类型互相可赋值，防止两头漂移。
- **`components` 用 `.default([])` 兜底**：模型省略组件列表时 schema 自动补空数组，服务层再归一化一次保证非空（`withStructuredOutput` 的返回类型把 default 字段视为可选）。
- **方舟模型不支持 `response_format: json_schema`**，沿用阶段四的结论：`withStructuredOutput` 必须显式传 `{ method: 'functionCalling' }` 走 tools 协议。

### System Prompt：组件选型指南 + 固定流程编排

Prompt 里写两类约束：一是「什么场景用什么组件」（决策用 selection、结构化收集用 form、执行前确认用 confirmation、单实体详情用 card、批量数据用 table……）；二是需求提交流程的**固定编排**——提新需求先出 selection 选类型，选定后才出 form，详情齐备才出 confirmation（可搭配 steps）。没有流程编排时首轮实测模型直接跳到 form（把类型选择做成了表单里的 select 字段），补上「一次只推进一步」的显式编排后稳定命中 selection。

### 确定性状态机（UiFlowService）

- 会话状态 `Map<sessionId, { stage, collectedData, history, updatedAt }>`，容量上限 500、写入时按 updatedAt 淘汰最旧。
- 转移表：selection.select → `collect_details`（回 form）；form.submit → `confirm`（回 confirmation + steps，必填字段缺失抛 400）；confirmation.confirm → `analyzing`（回 steps）/ 取消 → 退回 `collect_details`；table.row_select → card 详情；action_buttons.click 支持查看列表 / 查看报告 / 再提需求（重置流程）。
- payload 类型与组件类型不匹配（如 selection 收到 confirm）、行越界、未知 actionId 一律 `BadRequestException`，状态机不被脏操作推进。
- chat 路径复用同一会话存储：`recordUserInput` 返回历史 + 阶段 + 已收集数据喂给 LLM，`recordAssistantResponse` 把模型回复（message + 组件类型列表）写回历史。

### 鉴权与模块

`UiChatController` 带 `@UseGuards(JwtAuthGuard)`，因此 **LlmModule 需要 imports: [AuthModule]**（此前 LlmModule 里全是无守卫路由，app.controller.spec 组装真实模块时暴露）。服务注册在 LlmModule：providers/exports 增加 `UiResponseService`、`UiFlowService`。

## 交互闭环迭代：四阶段状态机（feat/ai-ui 第二个任务书）

第一个版本的状态机是五阶段（intake → collect_details → confirm → analyzing → completed），第二个任务书把它收敛为**规范的四阶段**，并调整各阶段的组件组合：

| Stage | 组件 | 转移 |
|---|---|---|
| `select_type` | selection（需求类型：functional/experience/tech） | select → `fill_detail` |
| `fill_detail` | form（需求详情） | submit → `confirm`；确认取消 → 回退到这里 |
| `confirm` | confirmation（确认提交分析）+ card（需求信息卡） | confirm=true → `result`；confirm=false → 回退 `fill_detail` |
| `result` | steps（分析进度，currentStep 3/4）+ action_buttons（查看报告/查看列表/再提需求） | new_requirement → 重置回 `select_type` |

设计要点：
- **回退是显式转移**：`confirm=false` 回到 `fill_detail` 并重新下发 form，回退后可重新提交再次到达 `confirm`（有单测覆盖「回退不破坏状态机」）。
- `handleAction` 每次返回都携带最新 `context`（sessionStage + collectedData），前端无需额外查询会话状态。
- LLM 路径的 System Prompt 同步改为四步编排（selection → form → confirmation+card → steps+action_buttons），与状态机的阶段语义一一对应；自由输入仍由模型按指南选组件，UI 操作回传仍全部走确定性状态机。
- 需求类型选项 id 规范为 `functional/experience/tech`，但状态机对未知 id 做兜底（直接用 id 当 label），因为 Stage 1 的 selection 是模型生成的，选项 id 不受我方控制。

验证（同一 sessionId 依次操作）：
1. chat「我要提一个新需求：用户希望能够批量导入 Excel 数据」→ selection（功能/体验/技术需求）
2. `select functional` → fill_detail + form
3. `submit form` → confirm + confirmation（6 条摘要）+ card（需求信息：Excel 批量导入）
4. `confirm` → result + steps（3/4）+ action_buttons（查看分析报告/查看需求列表/再提一个需求）
5. 回退：`confirm=false` → fill_detail + form
全量测试 **152/152** 通过，typecheck 绿。

## 参考教程代码后的优化（feat/ai-ui 第三个任务）

对照教程版 `UIFlowService` 做了评审，吸收三点、拒绝三点（拒绝的：关键词意图路由——我们已有 LLM 路径且关键词匹配脆弱；只按 stage 分发不看组件——粒度反而更粗；教程私有的组件字段——破坏类型与 schema 双向校验）。

采纳并落地：
1. **阶段守卫（最有价值）**：旧实现按 `action.componentType` 分发、不检查 session 阶段，`select_type` 阶段直接 POST `form.submit` 就能跳过类型选择推进到 `confirm`。现在维护「推进型交互 ↔ 阶段」绑定表（selection.select→select_type、form.submit→fill_detail、confirmation.confirm→confirm），乱序操作**不推进、重发当前阶段组件**（selection / form / confirmation+card / steps+action_buttons），而不是抛 400。table 行选择、card/action_buttons 点击不推进阶段，任意阶段放行。组件与 payload 配对错误仍属客户端 bug，保持 400。
2. **rawInput 预填**：`recordUserInput` 把用户最近一句原话存进 collectedData，进入 `fill_detail` 时表单描述字段带 `defaultValue` 原话，省一次输入。协议相应扩展：`FormField.defaultValue`（ui-types + ui-schemas 同步加，编译期双向校验兜住）。
3. **LLM 503 降级**：controller 捕获 `ServiceUnavailableException` 后返回 `UiFlowService.buildDefaultEntry`（快捷操作按钮：提交新需求/查看需求列表，按钮 id 与状态机既有 handler 对齐）；其他错误（如模型输出解析失败）照常抛出不降级。

验证：
- 新增单测 9 个（乱序守卫 4 + 非阶段绑定放行 + 预填 + 降级入口 + controller 降级/不降级），全量 **161/161**，typecheck 绿。
- curl 实测：新会话直接 `form.submit` → 重发 selection、stage 不变；chat 原话「…批量导入 Excel 数据」→ 选类型后表单 description.defaultValue 为原话；confirm 阶段乱序 `form.submit` → 重发 confirmation + card，且 card 内容是**先前已提交**的摘要而非乱序 payload。
- 环境插曲：机器重启导致 Docker daemon 掉线，prisma 集成测试失败；`open -a Docker` + `docker start compose-postgres-1` 恢复。

## generate 接口：无状态纯生成（feat/ai-ui 第四个任务）

参考教程的 `POST generate` 评估后采纳了接口本身、重写了实现。三个入口正好对应三种执行模式：

| 接口 | 状态 | 执行者 | 语义 |
|---|---|---|---|
| `POST chat` | 有状态（sessionId） | LLM | 对话推进，带历史与流程阶段 |
| `POST action` | 有状态 | 确定性状态机 | UI 操作回传 |
| `POST generate` | **无状态** | LLM | 纯文本 → UI 组件的一次性转换 |

教程实现的四个问题与修正：
1. 降级走 `handleInput('ui-generate-fallback', …)`——全局共享假 session，所有调用者状态互相污染，且把无状态请求降级成有状态流程输出。修正：**无状态接口的降级同样无状态**，返回静态快捷操作 `AIUIResponse`，不经过 UiFlowService、不建 session。
2. catch-all 吞错误只打 error name。修正：只对 `ServiceUnavailableException` 降级，其余（如模型输出解析失败）照常抛出，与 chat 路径同一规范。
3. 无鉴权、无校验。修正：沿用类级 `JwtAuthGuard`，input 非空校验、context 必须是对象。
4. `context` 是裸 `Record<string, unknown>`。修正：收成 `UIRequestContext`（sessionStage/collectedData），LLM 拿到的上下文才有语义。

验证：新增单测 4 个（透传 + 无状态不触碰会话、503 静态降级、其他错误抛出、400），全量 **164/164**；curl 实测：结论文本 → `card`（需求分析结论卡）；生产指标文本 → `table`（3 列 3 行，含环比）；input 缺失 → 400。

## 完整流程回归：五阶段同一 sessionId（feat/ai-ui 第五个任务）

按教程脚本做端到端回归，前做了两处小适配：

1. 表单增加可选字段 `acceptanceCriteria`（验收标准，textarea）——教程脚本的 formData 带此字段，且它本来就是需求分析业务的真实字段；同步进 FIELD_LABELS，确认摘要/信息卡都会展示。
2. System Prompt 流程编排增加第 0 条：打招呼或无明确业务意图 → 返回 action_buttons 常用服务入口，不展开流程。

脚本本身两处与实现的差异（不改代码，按实现修正脚本）：
- Stage 3 脚本用 `title`，我们表单下发的是 `name`——**表单字段名以服务端下发的 form 组件为准**（前端渲染 form 时天然拿到正确字段名），脚本硬编码教程自己的字段名才会对不上。
- Stage 4 脚本预期 steps + card + action_buttons，我们的 result 阶段是 steps + action_buttons（第二版任务书明确），card 在 confirm 阶段展示。
